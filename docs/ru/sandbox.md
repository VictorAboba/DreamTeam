# Песочница Docker и сессии без интернета

[English](../en/sandbox.md) · **Русский** · [Вся документация](README.md)

## Песочница Docker

```bash
dreamteam sandbox ~/DreamTeam --goal "..."
```

Команда собирает образ `dreamteam:latest` и запускает DreamTeam в контейнере. Домашняя папка монтируется в `/swarm`,
стартовая страница доступна на `127.0.0.1:8765`. Альтернатива: `SWARM_DIR=~/DreamTeam docker compose up --build`
с токеном, который вы задаёте сами (см. [Токен доступа](#токен-доступа)).
Локальные модели (Ollama, vLLM) из контейнера доступны по адресу `http://host.docker.internal:<порт>`.
В контейнер монтируется только домашняя папка, поэтому сессии, перенесённые командой `/cd` в папку вне неё, в
песочнице не запустятся: `dreamteam sandbox` перечисляет их при старте. Перед запуском верните такие сессии в
домашнюю папку (`/cd --default` или `/cd` в папку внутри неё: такие папки находятся и в контейнере).

### Токен доступа

Внутри контейнера хаб вынужден слушать `0.0.0.0`: порт, который публикует Docker, приходит на сетевой интерфейс
контейнера, а не на его loopback. Значит, до него могли бы достучаться и другие контейнеры в той же сети Docker.
Поэтому `dreamteam sandbox` при каждом запуске контейнера создаёт новый случайный токен, и хаб отклоняет любой запрос
не с loopback самого контейнера, если в нём нет этого токена (HTTP 401; WebSocket закрывается). При старте команда
печатает:

* адрес доски с `?token=...`: хаб превращает его в cookie (HttpOnly, SameSite=Strict) и открывает адрес без токена;
* команду для Claude Code с заголовком:
  `claude mcp add --transport http dreamteam http://127.0.0.1:8765/mcp --header "Authorization: Bearer <токен>"`.
  Токен меняется при каждом запуске; `claude mcp add dreamteam -- dreamteam mcp` продолжает работать и после
  перезапуска, потому что находит токен сам.

Пока контейнер работает, токен хранится на хосте в `~/.dreamteam/hub-tokens/<порт>.json` (вне смонтированной папки;
место меняет `DREAMTEAM_TOKENS_DIR`), и `dreamteam console`, `tui`, `mcp`, `status` и `serve` на этом компьютере сами
отправляют его хабу на `127.0.0.1:<порт>`. Они берут его заново для каждого запроса, поэтому консоль, TUI или
`dreamteam mcp`, который держит запущенным Claude Code, продолжают работать, когда песочница перезапускается с новым
токеном. Если эта папка оказалась внутри смонтированной домашней, токен не сохраняется: задайте для этих команд
`DREAMTEAM_HUB_TOKEN=<токен>`. То же касается библиотеки навыков хоста, которая тоже монтируется: токен никогда не
сохраняется внутри папки, которую видит контейнер. Если есть и то и другое, команды сначала пробуют сохранённый
токен, а сразу за ним `DREAMTEAM_HUB_TOKEN` (файл токена, переживший свою песочницу, потому что команду убили, не
мешает).

Команды DreamTeam отправляют токен только хабу на loopback-адресе, а `DREAMTEAM_HUB_TOKEN` — ещё и по адресу хаба,
который вы указали в командной строке: `dreamteam console --url http://192.168.1.5:8765` с заданным
`DREAMTEAM_HUB_TOKEN` достаёт до хаба на другом компьютере. Адрес из `hub.json` (он лежит в смонтированной папке, куда
могут писать агенты) получает токен, только если это loopback-адрес, поэтому указывайте в `--url` только адрес хаба,
который запустили сами. Консоль `dreamteam serve` и `run` и TUI отправляют `DREAMTEAM_HUB_TOKEN` хабу, который
обслуживают сами, на любом адресе. К хабу на `127.0.0.1`, `localhost` или `[::1]` команды DreamTeam обращаются напрямую,
никогда не через прокси из `HTTP_PROXY`, который увидел бы токен.

`dreamteam sandbox` никогда не передаёт в окружение контейнера сам токен, только его SHA-256
(`DREAMTEAM_HUB_TOKEN_SHA256`). Хаб сравнивает с ним SHA-256 того, что прислал запрос, так что по хешу никто не войдёт.
Кроме того, DreamTeam при старте убирает обе переменные из своего окружения: они не попадают ни в команды агентов, ни в
MCP-серверы, ни в git самого DreamTeam, что бы ни разрешал `shell.pass_env`. Страница на другом порту `127.0.0.1` доской
не воспользуется: запрос, у которого есть только cookie, должен прийти с origin самой доски (схема, хост и порт).

Хаб на адресе, отличном от loopback, без токена не запускается: команда образа по умолчанию (`serve --host 0.0.0.0`)
с обычным `docker run` или `docker compose` без токена завершается с ошибкой, в которой сказано, что задать (с
`docker compose up -d` её показывает `docker compose logs`), прежде чем что-либо создать или запустить. То же самое
делают `dreamteam serve`, `run` и TUI с `--host 0.0.0.0` (или таким `server.host`) на любом компьютере. С
`docker compose` задайте `DREAMTEAM_HUB_TOKEN` на хосте сами (`docker compose ps`, `logs` и `down` работают и без
него):

```bash
export DREAMTEAM_HUB_TOKEN=$(python3 -c "import secrets; print(secrets.token_urlsafe(32))")
SWARM_DIR=~/DreamTeam docker compose up --build
# доска: http://127.0.0.1:8765/?token=<токен>
```

В PowerShell: `$env:DREAMTEAM_HUB_TOKEN = python -c "import secrets; print(secrets.token_urlsafe(32))"`. С обычным
`docker run` передайте `-e DREAMTEAM_HUB_TOKEN_SHA256=<SHA-256 токена>` (или `-e DREAMTEAM_HUB_TOKEN`) и задайте
`DREAMTEAM_HUB_TOKEN=<токен>` для команд на хосте. Лучше передавайте `DREAMTEAM_HUB_TOKEN_SHA256`: тогда самого
токена в окружении контейнера нет. `DREAMTEAM_HUB_NO_TOKEN=1` всё же запускает хаб без токена (с предупреждением в
логе): тогда рой контролирует любой контейнер его сети.

## Сессия без интернета

Для бенчмарков и недоверенных задач сессии можно отключить интернет: флажок «Без интернета для агентов» в диалоге
новой сессии, поле «Интернет для команд агентов» в ⚙ сессии, `[swarm] network = "off"` в настройках,
`--network off` у `dreamteam`, `serve --goal`, `run` и `sandbox`, `network: "off"` у `session_create`. Сеть теряют
команды агентов (`shell`), их фоновые процессы и MCP-серверы, которые запускает DreamTeam; сам DreamTeam (вызовы
LLM, порт доски) сеть сохраняет, localhost работает. Агенты узнают об этом из уведомления, а не перебором. Насколько
это строго, зависит от машины, и интерфейс говорит об этом прямо:

* **Docker** (`dreamteam sandbox`): команды идут от отдельного пользователя, чьи пакеты, кроме loopback, отбрасывает
  файрвол контейнера; порт доски для него тоже закрыт (иначе через её API агент мог бы включить сеть обратно). Если
  смонтированная папка принадлежит обычному пользователю (Linux), команды идут от его uid и файлы агентов остаются
  вашими; иначе (Docker Desktop, том Docker) — от `dreamteam-agent` из образа. Права ваших файлов DreamTeam не
  меняет: группу и права на запись получает только то, что создал root в контейнере. Право `NET_ADMIN` контейнер
  получает, только когда без сети нужна хотя бы одной сессии (флаг `--network off`, настройки или уже созданная
  сессия), и DreamTeam сбрасывает его сразу после настройки файрвола. Образ, собранный по старому Dockerfile, в этом
  случае пересобирается сам. Сессия, у которой сеть отключили позже в контейнере без файрвола, получает только
  вариант «по возможности» (см. ниже), пока песочницу не перезапустят: интерфейс так и подсказывает.
* **Linux**: команды запускаются в отдельном сетевом пространстве, где есть только свой localhost; от своего
  пользователя, как и раньше. Пространство одно на процесс DreamTeam: сервер, запущенный одной командой в фоне, виден
  следующим командам, тестам и MCP-серверам, а localhost самой машины (доска, ваша локальная база) — нет. Если ядро
  не даёт пользовательских пространств имён, остаётся вариант «по возможности».
* **Windows и macOS — по возможности, это не изоляция**: прокси-переменные указывают на закрытый порт, pip, uv,
  npm, cargo, go и git переведены в офлайн, MCP-серверы с удалённым адресом в команде не подключаются. Программа,
  которая этого не учитывает (сырой сокет, веб-команды Windows PowerShell 5.1), в сеть выйдет, и API доски на
  localhost агенту доступен.

Пока сеть отключена, зависимости скиллов, которые предложили агенты, не устанавливаются (иначе предложение было бы
обходом); уже готовые окружения работают. Ваши собственные скиллы ставятся как обычно: их ставит DreamTeam, а не
агент. Собственные команды git самого DreamTeam не запускают git-хуки, `core.fsmonitor`, а также фильтры и помощники,
которые агент вписал в конфиг репозитория, — с сетью и без неё; сработать может только настройка, которую команда
агента записывает ровно в тот момент, когда стартует git самого DreamTeam (см. [Безопасность](security.md)). В Docker
и на Linux каждая команда git, которую DreamTeam запускает для такой сессии (коммиты, проверки вашей папки, коммиты
при `/cd`), ещё и работает так же, как команды агентов (от того же пользователя в Docker, в том же сетевом
пространстве имён на Linux), с самого старта сессии; если отключить сеть в ⚙, следующая команда git самого DreamTeam
дождётся, пока сможет работать так же: если что-то всё же проскользнёт, у него будет не больше прав и сети, чем у
агентов. Изменение в ⚙ действует на новые команды; уже запущенные фоновые процессы сохраняют прежний режим.
