# Безопасность

[English](../en/security.md) · **Русский** · [Вся документация](README.md)

* Агенты выполняют команды и код MCP-серверов с правами пользователя, который запустил рой. Для недоверенных
  задач используйте `dreamteam sandbox` (Docker). Сессия без интернета (`network = "off"`) строго отрезана от сети
  только в Docker и на Linux; на Windows и macOS это лишь прокси и офлайн-настройки.
* Фоновые процессы агентов работают с теми же правами в папке сессии. Они не переживают свою сессию: её
  остановка, удаление или перенос (`/cd`) останавливают их вместе со всем, что они запустили (в Windows — Job
  Object, в Linux и macOS — группа процессов и сторожевой процесс; так же и после сбоя сервера). Их вывод
  хранится в `.scratch/<агент>/jobs/`. В песочнице Docker порты, которые открывают агенты (dev-серверы), наружу
  не публикуются.
* Сессия, подключённая командой `/cd` к вашему проекту, правит его файлы и коммитит в текущую ветку. Перед
  переносом переключитесь на отдельную ветку, если не хотите видеть коммиты агентов в основной.
* Секреты (`*_API_KEY`, `*_TOKEN`, `*SECRET*`, …) не передаются в консоль агентов и их MCP-серверы,
  если вы явно не разрешили их в `shell.pass_env`.
* Агенты могут менять `.git` сессии из своей консоли. Поэтому собственные команды git самого DreamTeam (автокоммиты,
  проверки вашей папки) никогда не запускают то, что репозиторий велит git запустить: хуки, `core.fsmonitor`, фильтры,
  драйверы textconv и слияния, ssh- и credential-помощники из `.git/config`, подключённых файлов и подмодулей. Они
  работают без переменных, которые консоль агентов считает секретами (в том числе тех, что `shell.pass_env` туда
  пропускает), и без сетевого доступа для git. Ваши собственные фильтры из глобального или системного конфига git
  (git-lfs) продолжают работать. Фильтр, который задан только в конфиге самого репозитория и помечен обязательным
  (git-crypt или git-lfs, установленный с `--local`), там запустить нельзя: такие файлы DreamTeam не включает в свои
  коммиты (а не сохраняет их без фильтра) и не учитывает в проверках вашей папки (их изменения не мешают запустить
  сессию; в подмодуле со своим таким фильтром файл, который только задели, всё ещё считается изменением подмодуля, пока
  его не увидит ваш собственный `git status`), о чём один раз пишет в лог: коммитьте их своим git. Так работает git с
  версии 2.13 (в git до 2.44, как в macOS и Debian 12, такие файлы исключаются по имени). Одно ограничение остаётся:
  настройка, которую команда агента записывает ровно в тот момент, когда стартует git самого DreamTeam, всё ещё может
  сработать. В сессии без сети в Docker и на Linux каждая команда git, которую DreamTeam запускает для неё (автокоммиты,
  проверки вашей папки, коммиты при `/cd`), работает так же, как команды агентов, поэтому такая настройка выполнится с
  правами агентов и без сети. В остальных случаях — от пользователя DreamTeam, с тем же отфильтрованным окружением.
* Вне Docker команды агентов работают от того же пользователя, что и DreamTeam (на Linux без сети тоже: отделена там
  только сеть), поэтому запущенная ими программа может прочитать всё, что доступно пользователю DreamTeam. То, что
  секретов нет ни в окружении агентов, ни в git самого DreamTeam, не даёт DreamTeam передать их самому; от такой
  программы это не защищает.
* Хаб по умолчанию слушает только `127.0.0.1` и не требует авторизации. Не открывайте его в сеть без обратного
  прокси с авторизацией или без токена: если задан `DREAMTEAM_HUB_TOKEN`, любому запросу не с loopback самого хаба
  нужен этот токен (заголовок `Authorization: Bearer <токен>` или cookie, которую ставит адрес доски с `?token=`);
  без него ответ — 401. Хаб сравнивает SHA-256 того, что прислал запрос, с SHA-256 токена за постоянное время (ему
  достаточно одного `DREAMTEAM_HUB_TOKEN_SHA256`). Запрос, у которого есть только cookie, должен прийти с origin самой
  доски: браузеры отправляют cookie на любой порт `127.0.0.1`. Хаб на адресе, отличном от loopback, без токена не
  запускается, если не задан `DREAMTEAM_HUB_NO_TOKEN=1`.
* Токен защищает только прямую привязку к адресу, отличному от loopback. Любой клиент с loopback самого хаба
  обходится без него, поэтому всё, что на том же компьютере пересылает соединения хабу (обратный прокси, `ssh -R`,
  socat, агент туннеля), пускает своих клиентов без токена: такому посреднику нужна своя авторизация. Хаб никогда не
  учитывает `X-Forwarded-For` и `Forwarded` (что бы ни говорил `FORWARDED_ALLOW_IPS`), так что заголовком удалённого
  клиента в loopback не превратить.
* В песочнице Docker хаб внутри контейнера слушает `0.0.0.0` (опубликованный порт не доходит до loopback
  контейнера), поэтому до его порта достают и другие контейнеры в той же сети Docker. Поэтому `dreamteam sandbox`
  даёт каждому контейнеру свой токен, хранит его на хосте вне всех папок, которые монтирует (см.
  [Песочница Docker](sandbox.md#токен-доступа)), а контейнеру даёт только его SHA-256.
* Защита от DNS-rebinding и межсайтовых запросов действует при любом адресе привязки (включая `0.0.0.0` в Docker):
  через `localhost` доступ есть всегда, по IP — если это адрес, на который пришло соединение (с токеном — любой IP);
  другие имена хостов перечислите в `DREAMTEAM_ALLOWED_HOSTS=board.example.com`. `DREAMTEAM_PUBLIC_URL` задаёт адрес
  доски, который видят пользователи (его выставляет `dreamteam sandbox`).
* `docker compose up --build` отправляет в Docker только исходники (`.dockerignore`): ни `.venv`, ни `.git`, ни папки
  роёв с их базами и `dreamteam.toml` с ключами в образ не попадают.
