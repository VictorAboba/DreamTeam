# Безопасность

[English](../en/security.md) · **Русский** · [Вся документация](README.md)

* Агенты выполняют команды и код MCP-серверов с правами пользователя, который запустил рой. Для недоверенных
  задач используйте `dreamteam sandbox` (Docker). Сессия без интернета (`network = "off"`) строго отрезана от сети
  только в Docker и на Linux; на Windows и macOS это лишь прокси и офлайн-настройки.
* Фоновые процессы агентов работают с теми же правами в папке сессии. Они не переживают свою сессию: её
  остановка, удаление или перенос (`/cd`) останавливают их вместе со всем, что они запустили (в Windows — Job
  Object, в Linux и macOS — группа процессов и сторожевой процесс; так же и после сбоя сервера). Их вывод
  хранится в `.scratch/<агент>/jobs/`. В песочнице Docker порты, которые открывают агенты (dev-серверы), наружу
  не публикуются.
* Сессия, подключённая командой `/cd` к вашему проекту, правит его файлы и коммитит в текущую ветку. Перед
  переносом переключитесь на отдельную ветку, если не хотите видеть коммиты агентов в основной.
* Секреты (`*_API_KEY`, `*_KEY`, `*_TOKEN`, `*_PAT`, `*SECRET*`, `*PASSWORD*`, …) не передаются в консоль агентов и
  их MCP-серверы, если вы явно не разрешили их в `shell.pass_env`. Пароль или токен в URL
  (`PIP_INDEX_URL=https://user:password@…`, `DATABASE_URL=postgres://user:password@…`, адрес прокси, в том числе
  без схемы, как `HTTPS_PROXY=user:password@host:3128`) там убирается из значения: переменная по-прежнему указывает
  на тот же индекс или базу, только без учётных данных. Установщики зависимостей ваших собственных скиллов и
  MCP-серверы из `[mcp.external]` сохраняют учётные данные в URL, но переменных с именами секретов тоже не получают:
  передайте их серверу из `[mcp.external]` в его таблице `env` или через `shell.pass_env`, а установщикам ваших
  собственных скиллов — через `[skills] install_env`.
* При `[mcp] require_approval = true` вы одобряете снимок MCP-сервера агента: код, прошедший автоматическую
  проверку, вместе с его зависимостями; снимок хранится вне рабочей папки, в `.dreamteam/mcp/<имя>/`. Карточка MCP и
  диалог в терминале показывают его SHA-256, и запускается именно снимок. Если `mcp/<имя>/server.py` в рабочей
  папке потом меняется, сервер при следующем запуске проверяется заново и снова ждёт вашего одобрения, а одобрение
  не проходит, пока этот файл отличается от снимка, или если агент создал сервер заново после того, как карточка или
  диалог показали его вам (они передают показанный SHA-256; `/approve <имя> <sha256>` в консоли и терминальном
  интерфейсе и `mcp_approve` принимают тот, что показывают `mcp_list` или карточка, целиком или первые 8 и более
  символов, а `/approve <имя>` без него в терминальном интерфейсе передаёт SHA-256 диалога, отложенного по Esc). Этот
  SHA-256 охватывает команду запуска и зависимости вместе с `server.py`, поэтому это не SHA-256 одного файла. Снимок
  запускается в папке `mcp/<имя>/`: файлы, которые сервер держит там, он открывает по относительным путям, а не
  через `__file__`. Одобренный вами (или созданный вами самими) сервер попадает в общую библиотеку вместе с
  одобрением, поэтому другая сессия, импортирующая ровно этот код, запускает его без вопроса; другой код из
  библиотеки по-прежнему ждёт одобрения. Агент не может заменить сервер библиотеки, который сохранила другая
  сессия, даже под тем же именем владельца. Без `require_approval` изменённый `server.py` проверяется заново при
  следующем запуске и используется без вопросов. Снимок недоступен файловым инструментам агентов, но не командам
  их консоли, а отметки об одобрении в библиотеке защищены не больше, чем сама папка библиотеки.
* [Экспорт](transfer.md) (`dreamteam export`) не выгружает ключи API профилей, значения `env` внешних MCP-серверов
  (только их имена), учётные данные в командах MCP-серверов и токены хаба. Прежде чем экспорт будет готов, каждый
  записанный файл, каждая строка баз сессий и вся история выгруженных git-репозиториев проверяются на известные
  секреты этого компьютера: сохранённые ключи, значения переменных с ключами и переменных, которые консоль агентов
  считает секретами, `shell.pass_env` и `[skills] install_env`, значения `env` и учётные данные команд MCP-серверов,
  токен хаба — в UTF-8 и в UTF-16. Значения короче 8 символов не ищутся, а такие короткие учётные данные команд
  остаются в скопированной базе сессии (более длинные из неё вырезаются). Если что-то найдено, экспорт удаляется, а
  сообщение называет место, но не значение. Другие токены, которые агенты вывели в историю или записали в файлы,
  проверка не знает, поэтому папку экспорта стоит беречь так же, как саму домашнюю папку. Одобрения MCP-серверов
  переезжают вместе с библиотекой: сервер, одобренный на одном компьютере, одобрен и на другом, поэтому
  импортируйте только свои экспорты. Импорт
  оставляет сохранённый ключ API (а также настроенные здесь переменную ключа и секретные поля `extra`), только пока
  у профиля те же провайдер и `base_url`, а значения `env` MCP-сервера — только для той же команды и папки.
* Агенты могут менять `.git` сессии из своей консоли. Поэтому собственные команды git самого DreamTeam (автокоммиты,
  проверки вашей папки) никогда не запускают то, что репозиторий велит git запустить: хуки, `core.fsmonitor`, фильтры,
  драйверы textconv и слияния, ssh- и credential-помощники из `.git/config`, подключённых файлов и подмодулей. Они
  работают без переменных, которые консоль агентов считает секретами (в том числе тех, что `shell.pass_env` туда
  пропускает), и без сетевого доступа для git. Ваши собственные фильтры из глобального или системного конфига git
  (git-lfs) продолжают работать. Фильтр, который задан только в конфиге самого репозитория и помечен обязательным
  (git-crypt или git-lfs, установленный с `--local`), там запустить нельзя: такие файлы DreamTeam не включает в свои
  коммиты (а не сохраняет их без фильтра) и не учитывает в проверках вашей папки (их изменения не мешают запустить
  сессию; в подмодуле со своим таким фильтром файл, который только задели, всё ещё считается изменением подмодуля, пока
  его не увидит ваш собственный `git status`), о чём один раз пишет в лог: коммитьте их своим git. Так работает git с
  версии 2.13 (в git до 2.44, как в macOS и Debian 12, такие файлы исключаются по имени). Одно ограничение остаётся:
  настройка, которую команда агента записывает ровно в тот момент, когда стартует git самого DreamTeam, всё ещё может
  сработать. В сессии без сети в Docker и на Linux каждая команда git, которую DreamTeam запускает для неё (автокоммиты,
  проверки вашей папки, коммиты при `/cd`), работает так же, как команды агентов, поэтому такая настройка выполнится с
  правами агентов и без сети. В остальных случаях — от пользователя DreamTeam, с тем же отфильтрованным окружением.
* Вне Docker команды агентов работают от того же пользователя, что и DreamTeam (на Linux без сети тоже: отделена там
  только сеть), поэтому запущенная ими программа может прочитать всё, что доступно пользователю DreamTeam. То, что
  секретов нет ни в окружении агентов, ни в git самого DreamTeam, не даёт DreamTeam передать их самому; от такой
  программы это не защищает.
* Хаб по умолчанию слушает только `127.0.0.1` и не требует авторизации. Не открывайте его в сеть без обратного
  прокси с авторизацией или без токена: если задан `DREAMTEAM_HUB_TOKEN`, этот токен нужен любому запросу, в том
  числе с компьютера самого хаба (заголовок `Authorization: Bearer <токен>` или cookie, которую ставит адрес доски
  с `?token=`);
  без него ответ — 401. Хаб сравнивает SHA-256 того, что прислал запрос, с SHA-256 токена за постоянное время (ему
  достаточно одного `DREAMTEAM_HUB_TOKEN_SHA256`). Запрос, у которого есть только cookie, должен прийти с origin самой
  доски: браузеры отправляют cookie на любой порт `127.0.0.1`. Хаб на адресе, отличном от loopback, без токена не
  запускается, если не задан `DREAMTEAM_HUB_NO_TOKEN=1`.
* Хаб с токеном требует его от всех клиентов, в том числе с собственного loopback: в песочнице Docker команды агентов
  приходят к хабу с loopback контейнера и без токена не могут пользоваться его API. Команды DreamTeam на хосте
  отправляют токен сами, а консоль `dreamteam serve` и `run` и TUI входят в хаб, который обслуживают, со своим
  токеном, который хранится только в памяти этого процесса. Всё, что на том же компьютере пересылает соединения хабу
  (обратный прокси, `ssh -R`, socat, агент туннеля), тоже никого не пускает без токена. Хаб никогда не учитывает
  `X-Forwarded-For` и `Forwarded` (что бы ни говорил `FORWARDED_ALLOW_IPS`). Хаб без токена (по умолчанию
  `dreamteam serve` на `127.0.0.1`) ничего ни от кого не требует: его API доступен любой программе на его компьютере,
  в том числе командам агентов вне Docker.
* В песочнице Docker хаб внутри контейнера слушает `0.0.0.0` (опубликованный порт не доходит до loopback
  контейнера), поэтому до его порта достают и другие контейнеры в той же сети Docker. Поэтому `dreamteam sandbox`
  даёт каждому контейнеру свой токен, хранит его на хосте вне всех папок, которые монтирует (см.
  [Песочница Docker](sandbox.md#токен-доступа)), а контейнеру даёт только его SHA-256.
* Защита от DNS-rebinding и межсайтовых запросов действует при любом адресе привязки (включая `0.0.0.0` в Docker):
  через `localhost` доступ есть всегда, по IP — если это адрес, на который пришло соединение (с токеном — любой IP);
  другие имена хостов перечислите в `DREAMTEAM_ALLOWED_HOSTS=board.example.com`. `DREAMTEAM_PUBLIC_URL` задаёт адрес
  доски, который видят пользователи (его выставляет `dreamteam sandbox`). Запрос из браузера (и WebSocket доски)
  должен прийти с адреса самой доски, с адреса из `DREAMTEAM_PUBLIC_URL` или с разрешённого имени: страница на другом
  порту `localhost` принадлежит другой программе, и её запрос отклоняется. Прокси на том же компьютере, который меняет
  заголовок `Host`, требует задать в `DREAMTEAM_PUBLIC_URL` адрес, который открывают пользователи. Если в адресе нет
  порта, адрес доски охватывает и другой стандартный порт этого имени (80 или 443), кроме `localhost`, `127.0.0.1` и
  `::1`: перед прокси, который снимает TLS, хаб не видит схему. Хабу с токеном там всё равно нужен
  `DREAMTEAM_PUBLIC_URL`.
* `docker compose up --build` отправляет в Docker только исходники (`.dockerignore`): ни `.venv`, ни `.git`, ни папки
  роёв с их базами и `dreamteam.toml` с ключами в образ не попадают.
* В образе Docker git не доверяет репозиториям другого владельца (его проверка `safe.directory` включена): команды
  агентов, их фоновые процессы и MCP-серверы сессии доверяют только папке этой сессии, папкам внутри неё и, если у
  папки нет своего репозитория, репозиторию, в котором она лежит; git самого DreamTeam называет тот единственный
  репозиторий, в котором работает. git отклоняет только репозитории другого пользователя: папки, созданные
  пользователем хоста (bind mount на Linux), или, для команд сессии без сети, папки, созданные root. С включённой
  сетью команды работают от root, которому принадлежат и все папки сессий, созданные DreamTeam, поэтому эта
  проверка не отделяет сессии друг от друга.
